## 7페이지 — 개발환경

이어서 실험을 진행한 개발환경과 학습·서빙 구조를 설명드리겠습니다.

저희는 구글 쿠버네티스 엔진, GKE 위에 실험 환경을 구성했습니다. Kubeflow Pipelines로 데이터 처리부터 Dispatcher 학습과 평가까지 자동화했고, KServe를 통해 모델을 배포해 온라인 추론 성능을 측정했습니다.

이번 환경에서는 GPU 없이 CPU를 사용했습니다. 또한 학습이나 부하 생성 작업이 추론 서버의 자원을 함께 사용하면 측정에 영향을 줄 수 있기 때문에, 역할별로 노드 풀을 분리했습니다.

[오른쪽 표를 가리키며]

시스템 운영, 학습, 추론, 부하 생성에 각각 별도의 노드 풀을 할당했고, 요청은 클러스터 내부에서 전송했습니다. 

## 8페이지 — KFP: Dispatcher 학습 자동화

KFP를 이용한 동적 모델 선택을 위한 Fully connected layer인 Dispatcher 학습을 자동화했습니다.

전체 추론 흐름부터 보겠습니다.

입력 이미지에서 특징을 추출하면, Dispatcher가 그 특징을 보고 사용할 Expert를 선택합니다. 이후 선택된 Expert가 최종 분류 결과를 반환합니다.

이번 CIFAR-10 실험에서는 ShuffleNet, MobileNet, ResNet56을 Expert로 사용했습니다. 여기서 저희가 학습시킨 것은 Exprt 모델이 아닌 어떤 모델을 선택할지 결정하는 Dispatcher입니다.

이 과정은 다섯 단계로 자동화했습니다.

먼저 입력을 검증하고 데이터를 분할합니다. 다음으로 특징과 각 모델의 예측, 라우팅 정답을 캐시로 생성합니다. 이 데이터를 이용해 Dispatcher를 학습하고 후보를 탐색한 뒤, 최종 평가용 데이터에서 성능을 측정합니다. 마지막으로 모델 정보와 평가 결과를 등록합니다.

이렇게 학습한 모델 선택 방식을 실제 온라인 서빙에 적용해 지연시간을 측정했습니다.

## 9페이지 — 연산량은 줄었지만 응답시간은 증가

먼저 두 가지 요청 처리 구조를 비교했습니다.

Direct는 입력 이미지를 ResNet56 하나로 바로 처리하는 방식입니다. Distributed는 특징 추출과 Expert 실행을 원격으로 나누어 처리하며, 요청당 내부 RPC가 두 번 발생합니다. 여기서 Dispatcher는 ResNet56의 정확도 이상을 가지면서 연산량은 낮게 학습된 것을 선택했습니다.

비교는 워밍업 200건 이후 평가 요청 2천 건으로 진행했습니다. 초당 요청은 5건, 동시 요청은 1건으로 설정했고 재시도는 없었습니다.

[오른쪽 표를 가리키며]

정확도는 Direct가 94.60%, Distributed가 94.65%로 비슷했습니다. 이 차이는 평가 데이터에서 정답 한 건에 해당하므로, 정확도가 개선됐다고 해석하기는 어렵습니다.

이론적 연산량은 약 16.2% 감소했습니다. 하지만 평균 응답시간은 약 10.4밀리초에서 25.8밀리초로 오히려 늘어났고, p95 지연시간도 증가했습니다.

**이론적 계산량을 줄이는 데는 성공했지만, 실제 응답속도 개선으로 이어지지 않았습니다.**

그래서 모델 계산 이외의 구간에서 어떤 비용이 발생하는지 추가로 분석했습니다.

## 10페이지 — 모델 계산보다 큰 데이터 변환 비용

병목을 확인하기 위해 별도의 실행에서 구간별 계측을 추가했습니다.

[왼쪽 그래프를 가리키며]

요청 한 건당 CPU 시간을 보면, 모델 실행에는 약 3.9밀리초가 사용됐습니다. 반면 데이터를 전송할 수 있는 형태로 바꾸고 다시 복원하는 직렬화·역직렬화에는 약 9.8밀리초가 사용됐습니다.

데이터 변환에 들어간 CPU 시간이 모델 실행의 약 2.5배였습니다.

기존 구조에서는 이미지와 특징을 JSON 숫자 문자열로 변환하고, 받는 쪽에서 다시 해석했습니다. 여기에 내부 HTTP 호출 두 번과 새로운 연결 생성 두 번이 반복됐고, 내부 전송 본문 크기는 합계 약 141킬로바이트였습니다.

따라서 최적화 대상은 모델 연산뿐 아니라 **데이터 변환과 연결 처리**까지 포함해야 했습니다.

~~여기서 그래프의 CPU 시간과 실제 응답시간은 서로 다른 지표이므로, 두 값을 단순히 더해서 전체 지연시간으로 해석할 수는 없습니다.~~

## 11페이지 — 통신 비용을 줄일수록 지연 감소

이 분석을 바탕으로 통신 비용을 줄이는 실험을 진행했습니다.

첫 번째는 Binary 방식입니다. 숫자 데이터를 JSON 문자열로 바꾸는 대신 바이너리 형태로 전달해 변환 비용을 줄였습니다.

두 번째는 Keep-alive입니다. 요청할 때마다 새 연결을 만드는 대신, 기존 연결을 재사용하도록 했습니다.

[막대그래프를 위에서 아래로 가리키며]

이번 최적화 실험의 기준 응답시간은 약 29.9밀리초였습니다. Binary를 적용하면 약 20.3밀리초, Keep-alive를 적용하면 약 25.8밀리초로 줄었습니다.

두 방식을 함께 적용했을 때는 약 16.7밀리초로, 기준 대비 평균 지연시간이 43.9% 감소했습니다.

또한 전체 모델을 하나의 Pod에 통합해 내부 RPC를 없앤 Fused 구조에서는 약 12.7밀리초까지 줄었습니다.

이 결과는 분산 구조에서 발생하는 데이터 변환과 연결 비용이 지연시간에 상당한 영향을 주고 있었다는 점을 보여줍니다.

Fused는 RPC를 없애 지연시간을 줄이지만 Fused에는 모델 확장 측면의 제약이 있습니다.

## 12페이지 — Hybrid: 통신은 줄이고, Expert는 독립 확장

Fused는 모든 모델을 하나의 Pod에 넣기 때문에, 특정 Expert에 요청이 몰리더라도 그 Expert만 따로 확장할 수 없어 전체 Pod를 함께 복제해야 합니다.

이 문제를 고려해 Hybrid 구조를 구성했습니다.

[왼쪽 구조도를 가리키며]

모든 요청이 공통으로 거치는 ShuffleNet 특징 추출과 Dispatcher를 Router Pod에 통합했습니다. MobileNet과 ResNet56은 별도의 Pod로 유지하고, 선택된 Expert만 원격으로 호출하도록 했습니다.

이렇게 하면 내부 RPC를 두 번에서 한 번으로 줄이면서, Expert별 독립 확장이 가능한 구조를 유지할 수 있습니다. 남아 있는 통신에는 Binary와 Keep-alive를 적용했습니다.

[오른쪽 표를 가리키며]

평균 지연시간은 약 14.7밀리초로, 통신을 최적화한 Distributed보다 12.4% 감소했습니다.

다만 여기서 확인한 것은 지연시간 개선과 독립 확장이 가능한 구조입니다. 실제 부하가 늘어났을 때의 처리량이나 자동 확장 효과는 추가 검증이 필요합니다.

## 13페이지 — Hybrid도 Direct보다 빠르지 않았습니다

하지만 이 Hybrid 구조도 처음의 Direct보다 빨라지진 않았습니다.

평균 지연시간은 Direct가 약 10.4밀리초, Hybrid가 약 14.7밀리초였습니다. p95 지연시간 역시 Direct가 약 12.6밀리초, Hybrid가 약 17.1밀리초로 Direct가 더 낮았습니다.

즉, **통신 비용을 상당히 줄였지만, ResNet56 하나를 바로 실행하는 방식보다 빠른 추론은 달성하지 못했습니다.**

두 결과는 서로 다른 실험에서 얻었고 할당 자원도 달라, 구조 자체의 우열로 일반화하기에는 한계가 있습니다. 다만 이번에 측정한 조건에서는 목표한 속도 개선이 나타나지 않았습니다.

그 이유를 Expert 선택 분포와 실제 모델 실행 비용으로 나누어 살펴봤습니다.

## 14페이지 — 선택 분포와 실제 실행 비용의 영향

첫 번째는 Expert 선택 분포입니다.

[왼쪽 비율 막대를 가리키며]

실험에서 사용한 Dispatcher에서 MobileNet은 전체 요청의 32%, ResNet56은 68%에서 선택됐고, ShuffleNet에서 바로 끝나는 요청은 없었습니다.

즉, 모든 요청이 특징 추출과 Dispatcher를 거친 뒤 추가 Expert까지 실행했습니다.이 과정에서 특징 추출과 RPC 통신 시간이 항상 포함되었습니다.

두 번째는 FLOPs와 실제 실행시간의 차이입니다.

[오른쪽 표를 가리키며]

ShuffleNet과 ResNet56의 연산량은 약 11.5배 차이가 납니다. 하지만 별도로 측정한 실행시간은 약 1.3밀리초와 2.9밀리초로, 차이가 약 2.2배였습니다.

즉, **FLOPs가 크게 줄어도 실제 실행시간이 같은 비율로 줄어드는 것은 아닙니다.**

이 두 결과를 종합하면, 작은 모델을 선택해서 절약한 시간이 특징 추출, Dispatcher 실행, 남아 있는 통신 비용을 충분히 상쇄하지 못한 것으로 해석할 수 있습니다.

따라서 다음 단계에서는 연산량뿐 아니라 실제 실행 비용을 학습과 모델 선택 기준에 반영해야 합니다.

## 15페이지 — 실제 비용을 반영한 모델 선택으로

앞서 확인한 한계를 바탕으로, 향후 과제를 네 가지로 정리했습니다.

첫째, FLOPs만으로 비용을 판단하지 않고, 측정한 실행시간과 CPU 사용량을 학습 비용에 반영해야 합니다.

둘째, ResNet56 선택 비율이 68%였던 원인을 살펴보기 위해 데이터셋, Expert 조합, 학습 설정을 비교해야 합니다.

셋째, 현재는 모든 요청에서 추가 Expert를 실행하고 있으므로, 특징 추출 모델의 예측만으로 종료할 수 있는 비율과 그때의 정확도를 함께 평가해야 합니다.


다만 조기 종료 비율을 높인다고 성능이 반드시 좋아지는 것은 아닙니다. 정확도가 떨어질 수 있고, 기본 처리 비용도 남아 있기 때문에 실제 개선 여부는 후속 실험으로 확인해야 합니다.

이번 실험에서 얻은 핵심은, 동적 모델 선택의 효과를 모델의 연산량만으로 판단할 수 없다는 점입니다. 정확도와 함께 실제 서비스 전체에서 발생하는 비용을 평가해야 합니다.

이상으로 개발환경과 서빙 성능 실험, 그리고 개선 방향에 대한 설명을 마치겠습니다.
