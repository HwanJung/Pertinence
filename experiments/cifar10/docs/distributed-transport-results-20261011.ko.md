# Distributed serving 병목 분석 및 개선 결과

분산 구조의 주요 개선 대상은 내부 RPC의 JSON 직렬화와 반복적인 연결 생성이었다.
Binary 전송과 Keep-alive를 결합한 D3에서는 새 기준군 D0 대비 평균 지연 **43.9%**,
Pod CPU/request **50.1%** 감소를 관측했다. Hybrid는 추가로 지연을 줄였으며,
이번 측정에서 Fused의 지연과 CPU 사용량이 가장 낮았다.

이 문서는 문제 원인 식별 → 병목 측정 → 개선 방안 → 최종 결과 → 배치 판단 순서로 정리한다.
결과는 **계측 ON·구조별 1회 실행**이며, 반복 측정 기반의 성능 확정 결과는 아니다.

## 1. 문제 원인 식별: 확인된 기존 수치

2026-10-09 단일 실행의 Fused/Distributed mean은 각각 11.466/25.845 ms, p95는 13.519/30.379 ms였다. Extractor 구간 증가는 7.936 ms, 선택 expert 구간 증가는 6.482 ms였다. 기존 request CPU와 내부 wall의 계측 범위가 달라 54% JSON CPU/46% 통신이라는 원인 분해는 사용하지 않는다.

기존 Distributed의 평균 지연은 Fused보다 약 14.38 ms 높았다. 증가분은 거의 전부
Extractor와 선택 Expert의 두 원격 호출 구간에 집중됐고, Dispatcher 계산 시간은 거의
변하지 않았다. 예측·route·logits가 동일했으므로 내부 RPC의 데이터 변환과 연결 처리 비용을
우선 조사했다. 모든 요청이 두 번째 expert까지 호출하는 route 분포는 `[0, 640, 1360]`이었다.

이전 결과는 참고값이다. 아래 개선율은 새 runtime의 D0를 기준으로 계산하며,
기존 실행과 새 계측 ON 실행을 직접 섞어 비교하지 않는다.

## 2. 병목 측정과 확인한 원인

여기서 **arm은 비교 실험의 개별 조건(실험군)**을 뜻한다. 각 arm은 모델 종류가 아니라
**모델 배치 구조·내부 RPC 전송 형식·연결 재사용 여부**의 조합을 나타낸다.
D는 Distributed, H는 Hybrid, F는 Fused 구조를 가리킨다.

| Arm | 배치 구조 | 내부 RPC 전송 | 연결 방식 | 비교 목적 |
|---|---|---|---|---|
| **D0** | 완전 분산 | JSON | 호출마다 새 연결 | 개선 전 기준군 |
| **D1** | 완전 분산 | Binary | 호출마다 새 연결 | 전송 형식만 개선한 효과 측정 |
| **D2** | 완전 분산 | JSON | Keep-alive | 연결 재사용만 개선한 효과 측정 |
| **D3** | 완전 분산 | Binary | Keep-alive | 두 개선을 함께 적용한 효과 측정 |
| **H1** | 부분 통합(Hybrid) | Binary | Keep-alive | D3에서 ShuffleNet을 Router로 통합해 첫 원격 호출 제거 |
| **F0** | 전체 통합(Fused) | 없음 | 해당 없음 | 모든 모델을 한 프로세스에서 직접 실행하는 비교 기준 |

- **D0~D3**: Router, ShuffleNet, MobileNet, ResNet을 4개 Pod로 분리한다.
  Router가 ShuffleNet을 원격 호출하고, Dispatcher의 선택에 따라 MobileNet 또는 ResNet을
  다시 원격 호출한다. 이번 trace에서는 요청당 내부 RPC가 **2회**다.
- **H1**: ShuffleNet과 Dispatcher를 Router에서 실행하고, 선택된 MobileNet 또는 ResNet만
  원격 호출한다. 총 3개 Pod이며, 이번 trace에서는 요청당 내부 RPC가 **1회**다.
  route 0에서는 로컬 ShuffleNet logits를 재사용하므로 원격 호출이 없지만, 이번 trace에는
  해당 route가 없다.
- **F0**: 모든 모델을 1개 Pod의 한 프로세스에서 실행하므로 내부 RPC가 **0회**다.

Binary는 FP32 숫자를 JSON 문자열 대신 바이트로 보내는 방식이며 압축이나 양자화가 아니다.
Keep-alive는 이미 만든 HTTP 연결을 다음 호출에서도 재사용하는 방식이다.
외부 Loadgen→Router JSON API는 모든 arm에서 동일하다.
따라서 D0↔D1은 Binary 효과, D0↔D2는 연결 재사용 효과,
D3↔H1↔F0는 모델 통합 범위에 따른 효과를 비교한다.

Router와 Expert에 구간별 monotonic wall time·실행 thread CPU 계측을 추가했다.
요청 ID·expert 이름·호출 순번으로 양쪽 기록을 연결하고, 전송 body bytes와 실제 연결
생성·재사용 횟수를 측정했다. cAdvisor의 Pod 전체 CPU·메모리·throttling·재시작도 수집했다.

각 진단은 warm-up 200회 뒤 같은 trace 2,000건을 5 RPS, concurrency 1, retry 0으로 처리했다. 다음 codec CPU와 잔차는 request당 값이며 warm-up 요청을 제외했다. RPC wall에서 server의 서로 겹치지 않는 decode/model/output/encode/write wall을 뺀 값은 전송·스케줄링·대기 잔차다. 순수 네트워크 시간이 아니다.

| Arm | Mean ms (ON) | Codec thread CPU ms/request | 잔차 ms/request | 요청/응답 body bytes/request | 생성/재사용 연결 |
|---|---:|---:|---:|---:|---:|
| D0 | 29.853 | 9.787 | 2.865 | 120243.5 / 21233.1 | 4000 / 0 |
| D1 | 20.271 | 0.873 | 2.595 | 24931.2 / 4950.1 | 4000 / 0 |
| D2 | 25.806 | 9.710 | 2.846 | 120243.5 / 21233.1 | 0 / 4000 |
| D3 | 16.743 | 0.847 | 2.633 | 24931.2 / 4950.1 | 0 / 4000 |
| H1 | 14.662 | 0.407 | 1.357 | 12437.6 / 373.7 | 0 / 2000 |
| F0 | 12.692 | 0.000 | 0.000 | 0.0 / 0.0 | 0 / 0 |

F0의 원격 RPC 지표 0은 원격 호출이 없다는 뜻이다. 로컬 모델 계산 비용이 0이라는 뜻은 아니다. 계측 기록의 파일 I/O와 미계측 framework 처리도 잔차에 영향을 줄 수 있다. 전체 request CPU는 child span과 중복 합산하지 않았다.

D0에서는 요청당 내부 RPC codec CPU가 9.79 ms였으며, 두 호출의 요청·응답 body 합계는
약 141 KB였다. 본 측정 2,000건에 내부 RPC 4,000회와 실제 연결 생성 4,000회가 발생했다.
즉, 클라이언트의 연결 객체 재사용이 실제 TCP 연결 재사용으로 이어지지 않았다.

D0→D1에서 codec CPU는 **9.79→0.87 ms**, 약 91% 감소했고 body 합계는
**약 141→30 KB**, 약 79% 감소했다. 이는 FP32 배열을 JSON 숫자 문자열로 바꾸고
다시 해석하는 작업이 큰 개선 대상이었다는 근거다. CPU 시간과 wall time은 다른 지표이므로,
codec CPU 감소량을 전체 지연 감소의 정확한 원인별 비율로 환산하지 않는다.

## 3. 개선 방안과 구현

| 개선 | 구현 내용 | 비교 목적 |
|---|---|---|
| Binary 전송 | 작은 JSON 헤더와 little-endian contiguous FP32 본문 사용. 이미지 바이트는 요청당 한 번 생성해 재사용하고 Expert 응답은 ndarray에서 직접 인코딩 | 숫자↔문자열 변환과 전송량 감소 |
| Keep-alive | 내부 HTTP/1.1 연결을 지속 사용. Content-Length·idle timeout을 명시하고 연결별 처리를 분리하며 모델 실행 동시성은 1 유지 | 반복 연결 생성 비용 감소 |
| Hybrid | Router에서 ShuffleNet·Dispatcher를 실행하고 선택된 MobileNet/ResNet만 Binary RPC로 호출. route 0은 로컬 logits 재사용 | 첫 번째 원격 호출 제거 |
| Fused | 모든 모델을 한 프로세스에서 직접 호출 | 원격 RPC가 없는 비교 기준 |

Binary는 압축이나 양자화가 아니다. 예를 들어 이미지의 `3 × 32 × 32 = 3,072`개 숫자를
문자열 대신 각 4바이트 FP32로 보내므로 이미지 본문은 정확히 12,288 bytes다.
모델·FP32 정밀도·Dispatcher·외부 Loadgen→Router JSON API는 유지했다.
JSON을 기본 전송으로 유지하고 Binary와 Keep-alive는 독립적인 선택 옵션으로 제공한다.
실패 시 JSON 자동 fallback이나 추론 재시도는 하지 않는다.

Predictor 자원 합계는 모든 구조에서 4 CPU/4 GiB로 맞췄다. Distributed는 4개 Pod에 각각
1 CPU/1 GiB, Hybrid는 Router 2 CPU/2 GiB와 expert 2개에 각각 1 CPU/1 GiB,
Fused는 1개 Pod에 4 CPU/4 GiB를 할당했다. Modelcar 자원은 별도로 집계한다.

handshake 시간으로 해석하지는 않는다.

결합한 D3에서는 D0 대비 평균 **13.11 ms·43.9%**, p95 **43.6%**, Pod CPU/request **50.1%**

관측된 격차의 약 **76%를 완전 분산 구조를 유지하면서 제거**한 셈이다.
평균 지연 감소와 함께 전체 p95와 CPU도 줄었다.

Hybrid는 D3보다 평균 **2.08 ms·12.4%**, CPU **17.3%**가 낮았다.
이 trace에서는 요청당 내부 RPC가 2회에서 1회로 줄었다.

## 5. 배치 판단과 해석 범위

| 배치 요구 | 이번 결과에 근거한 판단 |
|---|---|
| 완전 분산 구조 유지 | Binary + Keep-alive인 **D3가 가장 유력한 개선 후보**다. 구조를 통합하지 않고 지연과 CPU를 크게 줄였다. |
| 선택 Expert의 원격 분리를 유지하면서 지연 추가 감소 | **Hybrid가 절충안**이다. 첫 RPC를 제거해 D3보다 추가 개선을 관측했다. |
| 이번과 같은 저부하 지연·CPU 효율 우선 | **Fused가 가장 유리하게 관측**됐다. 최대 처리량이나 확장성 우위를 뜻하지 않는다. |

사용자 요청에 따라 36회 반복 실험과 별도 계측 ON/OFF 비교를 생략했다.
따라서 신뢰구간·통계적 개선 통과 판정·최종 후보 확정은 하지 않는다.
계측 오버헤드를 분리하지 않았으므로 실제 운영에서 같은 절감률이 유지된다고 보장하지 않는다.

route 0은 이번 trace에 없으므로 원격 호출을 생략하는 해당 경로의 실측 성능은 포함되지 않는다.
비교 범위는 같은 serving node에서 5 RPS로 실행한 저부하 지연이며,
최대 처리량·autoscaling·cross-node 효과에 대한 결론은 내리지 않는다.
Production promotion은 수행하지 않았다.
